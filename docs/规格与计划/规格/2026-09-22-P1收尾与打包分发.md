## 1. 背景与目标

P1 桌面端服务层与工作台 UI 已全部交付（Plan 桌面服务 Task 1-13 + UI 迭代），仅剩备份恢复的 UI 入口未接线（服务与 IPC 均就绪）。当前应用只能以 `pnpm dev` 开发模式运行，没有可分发的产物。

本设计交付两件事：

1. **备份恢复 UI 入口** —— 补齐 P1 功能闭环；
2. **macOS 打包分发链路** —— 用 electron-builder 产出无签名（ad-hoc）arm64 的 DMG + zip，双击可用的离线 .app。

## 2. 范围

**做：**
- 恢复 UI（入口 + 三口令表单 + 结果反馈）

- x64 / universal 产物（先 arm64；目标架构选择是配置项）

## 3. 打包链路设计

### 3.1 事实基础（已核对）

- electron-vite 产物在 `apps/desktop/out/`：`main/index.js`、`preload/index.js`、`renderer/`。
- `@openfield/core`（TS 源码包）已被 `externalizeDepsPlugin({ exclude: [...] })` **打进** `out/main`，运行时不依赖 workspace 链接。
- 运行时外置依赖仅五个：`better-sqlite3-multiple-ciphers`（native）、`chokidar`、`adm-zip`、`zod`、`@hapi/sntp`。
- vault home 默认 `app.getPath('userData')/openfield`，可用 `--openfield-home=` 覆盖——打包后天然落在 `~/Library/Application Support/OpenField/openfield`，不污染 .app 包内。
- 离线现状：字体本地打包（@fontsource）、运行时零 CDN 依赖、NTP 仅手动按钮且失败降级。打包不改变这些性质。

### 3.2 electron-builder 配置

`apps/desktop` 新增 devDep `electron-builder`（实施时钉当前稳定大版本）与 `electron-builder.yml`：

- `appId: fun.meoo.openfield`（首发 tag 前可改，之后视作不可变）
- `productName: OpenField`
- `directories.output: release`，`release/` 进 .gitignore
- `files`: `out/**`（electron-builder 自动附带生产 node_modules；native `.node` 自动 asarUnpack）
- `mac.identity: null`（跳过签名；arm64 产物由打包器自动 ad-hoc 签名，满足 macOS 11+ 强制要求）
- `mac.target`: `[{ target: dmg, arch: [arm64] }, { target: zip, arch: [arm64] }]`
- `mac.category: public.app-category.productivity`
- `icon: build/icon.png`
- `package.json` 补 `author` 字段（electron-builder 校验需要，取值项目署名）

### 3.3 脚本

```
pnpm dist       # electron-vite build && electron-builder --mac --arm64   → DMG + zip
pnpm dist:dir   # electron-vite build && electron-builder --mac --dir    → release/mac-arm64/OpenField.app（未打镜像，快速验证）
```

### 3.4 已知风险与兜底

| 风险 | 兜底 |
| --- | --- |
| `better-sqlite3-multiple-ciphers` 与 Electron 44 ABI 不匹配 | §6 打包 smoke 强制启动产物并建库；不匹配则 electron-builder 自动重编（本机已有 Xcode CLT） |
| pnpm 布局下 electron-builder 收集 node_modules 失败 | 退化方案：把纯 JS 依赖也全部 `exclude` 进 bundle，仅外置 native 模块 |
| 无签名 zip 经浏览器下载带 quarantine，首次打开被 Gatekeeper 拦截 | 使用手册写明右键→打开；本机分发可用 `xattr -d com.apple.quarantine` |
| 图标无源 | §5 一次性生成本地资产 |

## 4. 备份恢复 UI

### 4.1 入口与流程

- 位置：概览视图锁定区（现有 `btn-create` / `btn-open` / `btn-backup` 一组）新增 **`btn-restore`「从备份恢复…」**；解锁态隐藏，与服务层「仅锁定态可恢复」硬闸一致。
- 点击 → `backup:pick`（main 弹 `dialog.showOpenDialog`，过滤 `.ofbackup`，默认目录 `app.getPath('downloads')`）→ 返回所选路径（取消返回 null）。
- 表单（恢复面板，选完文件展开）：所选文件名只读展示 + `restore-backup-pass`（备份口令）+ `restore-vault-pass`（新库口令）+ `restore-vault-pass2`（确认）。
- 前端先校验：三项非空、口令 ≥ 8 字符、两次一致；`backup:restore` 的 zod（`RestoreInput`）是最终把关。
- 成功 → 提示「已恢复，请用新库口令解锁」，状态刷新为 `hasVault: true`，复用现有 `vault:open` 流程。
- 失败 → §6 文案映射。

### 4.2 新通道 `backup:pick`

- `shared/ipc.ts` 的 `IPC_CHANNELS` 追加 `'backup:pick'`；main 侧 handler 为 async（`dialog.showOpenDialog`），走现有 `wrap()` 即可；preload 白名单机制自动放行，无需改动。
- 渲染层依旧不接触文件系统，路径只存在于 main 进程内存与 `backup:restore` 入参中。

## 6. 错误处理

错误码 → 用户文案映射集中在 renderer 一处（新增 `restoreErrorText()` 纯函数）：

| 场景 | 表现 |
| --- | --- |
| 备份口令错误 | 「备份口令不正确」 |
| 容器损坏 / 解包失败 | 「备份文件无法读取：可能已损坏」 |
| home 下已有 vault.db（服务层拒绝覆盖） | 「当前位置已存在资料库：恢复会覆盖整个资料库，请先迁移或删除旧库」 |
| 口令不满足 ≥8 / 两次不一致 | 前端拦截，不发 IPC |
| 其他 | 原始错误信息透出（现有 `IpcResult.error` 通道） |

打包侧失败面（ABI、node_modules 收集）由 §7 打包 smoke 在本地蒸馏为「能否启动建库」一个布尔信号。

## 7. 测试策略

1. **单测**（vitest）：`restoreErrorText()` 映射表、恢复表单校验纯函数（长度/一致性/非空）。
2. **E2E（dev 模式，扩展现有 Playwright 套件）**：建库→登记→导出备份→锁库→走恢复入口（选文件→输三口令）→用新口令解锁→verify 零问题。
3. **打包 smoke**（新 e2e 文件，`dist:dir` 后运行）：Playwright `_electron` 以 `executablePath` 指向 `release/mac-arm64/OpenField.app/Contents/MacOS/OpenField` 启动，`--openfield-home=` 指向临时目录，断言窗口出现且能创建资料库。这是 native ABI 的关键闸门。
4. 手工验收清单：DMG 拖装、zip 解压直开、右键打开流程、断网启动全功能。
